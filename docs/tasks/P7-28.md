## Why

Panel Classic's Format > Fill… and Format > Line… are stubs, and
Panel Modern's Fill Options…, Line Options… and Format Shape do
nothing. P7-24 added colour, weight, pattern and arrowhead submenus as
a stop-gap; they stay (user, 2026-11-01). This task adds the dialogs
that set every fill and line cell at once.

## Goal

1. **Fill dialog** (Format > Fill… in Panel Classic, Fill Options… in
   Panel Modern, and the shape context menu where it has a Fill row):
   fill colour, pattern, pattern colour and transparency
   (`FillForegnd`, `FillPattern`, `FillBkgnd`, `FillForegndTrans`),
   with a preview swatch, and OK, Cancel and Apply. The fields open
   with the selection anchor's resolved values.
2. **Line dialog** (Format > Line…, Line Options…): colour, weight,
   pattern, cap, transparency, begin and end arrowheads and their
   sizes, and corner rounding (`LineColor`, `LineWeight`,
   `LinePattern`, `LineCap`, `LineColorTrans`, `BeginArrow`,
   `EndArrow`, `BeginArrowSize`, `EndArrowSize`, `Rounding`), with a
   preview line, and OK, Cancel and Apply.
3. **Format Shape pane** (Panel Modern's `format.shape.pane`): a pane
   with Fill and Line sections built from the same forms, applying as
   the user changes a field, and following the selection.
4. **One undo step** per OK or Apply, over every selected shape. Cancel
   changes nothing, including after an Apply (Apply's step stays; only
   later edits are dropped).
5. **The command contract** (AGENTS.md section 6): `format.fill` and
   `format.line` with arguments apply without a dialog (CLI, control
   channel, MCP); without arguments they request the dialog. Disabled
   with no selection, with the reason.
6. Reuse the picker tables (`pickers::PATTERNS`, `ARROWS`, the
   colours) rather than new ones. If P7-27 has merged, read its single
   label table.

### Deviations and our own choices

- **`UiRequest` gained three variants** (`ShowFillDialog`,
  `ShowLineDialog`, `ShowFormatShape`), not two: the pane is a UI
  surface the command can only request, like the dialogs.
- **`format.shape.pane` toggles** the pane (a second run closes it):
  its data id is shared with Panel Classic's View > Toolbars "Format
  Shape" row (see open issue 2).
- **Labels**: the cap and arrow-size lists are the ShapeSheet
  reference's enumerations as short labels, stored as one table in
  `larrygram-commands` (`LINE_CAPS`, `ARROW_SIZES`) beside
  `LINE_PATTERNS`/`LINE_ARROWS` and drawn by the forms — the P7-27
  review rule (A6) applied to the two new lists. `format.line`'s
  `cap` takes `rounded`/`square`/`extended` (or 0..2) now.
- **Previews** are ours: stripes stand in for patterned fills, the
  dash rhythm and head shapes are the picker's own samples (the
  renderer's tables draw the real ones).
- **Out-of-lane touch** (small, with its own test context):
  `crates/ui/src/shapes_window.rs` — `ShapesWindow::handle_keys`
  consumed Enter (and the arrows) while a dialog or pane **text field**
  had focus, so no typed value could commit on Enter and Enter could
  drop a stencil master. It now defers while any text edit is focused.
  The contexts cross-check (`crates/ui/tests/contexts/crosscheck.rs`)
  classifies the three new ids with P7-08's `NO_ROW`/`ALLOWED`
  mechanisms (the P7-25 precedent). `builtins/mod.rs` re-exports the
  two new label tables.

### Open issues

1. **The transparency cells' unit.** The dialogs, `shape.transparency`
   and the renderer all read `FillForegndTrans`/`LineColorTrans` as a
   **fraction** 0..1, while the ShapeSheet reference spells them 0..100
   percent. The corpus has no `*Trans` cell to arbitrate. One fix
   belongs in the model/render layer (write path and `render::build`'s
   `rgba_of` together); the dialogs' percent fields keep the current
   pipeline convention.
2. **The View > Toolbars "Format Shape" row** (Panel Classic data)
   carries `command: format.shape.pane`, so toggling that classic
   toolbar also toggles the pane. The row is really about the classic
   `toolbar.format_shape` toolbar. A layout pass may drop the command
   link from the three `view.toolbars.format_shape` rows (they are
   this task's "Format Shape entries" but the count pin made the edit
   risky this late); until then `format.shape.pane` is a toggle and
   the coupling is cosmetic.
3. **Resolved values vs Visio defaults.** The fields show the values
   the model resolves, including the ShapeSheet table defaults (e.g.
   `LineWeight` 0 shows "0 pt", `BeginArrowSize` 0 shows "Very small")
   where Visio's dialog shows its own defaults (0.75 pt, medium). Our
   rule is the goal's "the anchor's resolved values"; revisit in the
   parity pass if the defaults read badly.
4. **The Fill dialog's pattern list** is the line-pattern table plus
   "None" (goal 6: reuse `pickers::PATTERNS`); Visio's fill patterns
   have their own names and up to index 40. Revisit with a fill-pattern
   name table if one lands.
5. **The Format Shape pane is a window anchored at the right edge**,
   not a docked pane beside Shape Data/Size & Position (the shell's
   owned region is the dialog arm). Docking it into the pane column is
   a small follow-up; `panes::FormatShape` is ready for it.
6. **Defensive arms**: `field_args`' unknown-field errors and
   `field_intent`'s `CommandId::parse` failure are unreachable in the
   app (the first two are covered by unit tests, the parse arm is one
   uncovered line).
7. **ADR number**: 0083 was the next free number when written; if
   P7-26 or another in-flight task wrote an ADR too, the master
   renumbers one of them.
