## Why

The user's manual pass of the alpha build (2026-11-05):

1. **Panel Classic offers no way to pick an arbitrary colour.** The
   Fill Color, Line Color and Text Color pickers list theme and
   standard colours; the "More Fill Colors…", "More Line Colors…" and
   "More Text Colors…" rows (`ui-spec/layouts/panel-classic.yaml`)
   do not open a colour chooser.
2. **Panel Modern's Design > Backgrounds gallery is empty.** The
   control lists the `backgrounds` run-time list, which has no
   entries. `Page::background` (`crates/model/src/page.rs`) already
   names a background page.

## Goal

1. **A custom colour, both layouts.** Each "More … Colors…" row opens
   one colour dialog: a hue/saturation/value picker (egui's colour
   picker is fine), a hex field (`#RRGGBB`), OK and Cancel. OK applies
   the colour to the selection through the same command the swatches
   dispatch (`format.set.fill.color`, the line and text colour
   commands) as one undo step, and the colour joins the picker's
   Recent Colors. Cancel changes nothing. Panel Modern's matching
   "More Colors…" rows use the same dialog. Real-input tests in both
   layouts: pick `#3A7F2C` through the hex field for fill, line and
   text, check the cells and the picture; Cancel leaves the cells
   unchanged.
2. **The Backgrounds gallery.** The gallery lists "No Background" and
   a few original backgrounds we design ourselves (for example a solid
   tint, a soft vertical gradient and a light grid; no Visio
   background designs, names or art). Choosing one creates (or reuses)
   a background page holding that design, sets the current page's
   `background` to it, and draws it behind the page's shapes. "No
   Background" clears the link. One undo step each. Background Color
   (the submenu) colours the background page's design. The background
   page and the link save to `.vsdx` and reopen (MS-VSDX: a page with
   `Background='1'` and the foreground page's `BackPage`). If the model
   or the writer lacks a piece of this, add it in this task and say so
   in the Result. Real-input tests in Panel Modern: apply each
   background, check the page's link and the picture, undo, and
   save/reopen.

### What was built

**1. A custom colour, both layouts.** Three openers —
`format.fill_color.custom`, `format.line_color.custom` and
`format.text_color.custom` — request one colour dialog
(`UiRequest::ShowColorDialog` with the role `fill`, `line` or `text`).
The dialog (`crates/ui/src/color_dialog.rs`) is one body for the three
roles: a hue/saturation/value picker, a `#RRGGBB` hex field, OK and
Cancel. OK applies the colour to the selection through the same
command the swatches dispatch (`format.set.fill.color`,
`format.set.line.color`, `text.font.color`) as one undo step, and the
colour joins the picker's Recent Colors (one shared list of ten, most
recent first, de-duplicated). Cancel changes nothing. The colour
pickers gained the "More ... Colors..." row per role (the Panel Modern
splits draw the same picker body, so their rows use the same dialog),
and the Panel Classic "More ... Colors..." toolbar rows
(`ui-spec/layouts/panel-classic.yaml`) now link the three openers.

**2. The Backgrounds gallery.** The `backgrounds` run-time list
(`crates/ui/src/lists.rs`) lists "No Background" and the three designs
below; each row dispatches `tools.backgrounds` with its label, which
creates (or reuses) the design's background page and sets the current
page's `Page::background` to it — one undo step covering the page, the
design shapes and the link. "No Background" (and `none`) clears the
link. `tools.background.color` (the Background Color submenu, its
`colors` list) recolours the design in place, one undo step: every
shape's `FillForegnd` derives from the one design colour
(`backgrounds::design_colors`), so generation and recolour share one
table. The design and the link save to `.vsdx` and reopen (the
`BackPage`/`Background` marks of ADR 0073; nothing was missing in the
model or the writer — `Page::background` was already mapped both ways,
and the renderer composites background pages per ADR 0020).

**The designs (our own, per the master note).** All three are drawn
as rectangle shapes with no asset files (so no `ATTRIBUTION.md`
rows):

- **Solid Tint** → page "Background Tint": one full-page rectangle in
  the colour (default `#D6E4F0`).
- **Soft Gradient** → page "Background Gradient": 24 horizontal bands,
  the colour at the top fading to white at the bottom (default
  `#7FB2E5`).
- **Light Grid** → page "Background Grid": a near-white field (the
  colour mixed 18 % into white) with light grid lines at whole inches
  (the colour mixed 45 % into white), thin filled rectangles (default
  `#9DC3E6`).

### Deviations

1. **The picker is ours, not egui's.** egui's stock colour picker
   draws a clipboard glyph (`📋`) the bundled fonts cannot draw, and a
   missing glyph panics (AGENTS.md section 6): opening it crashed the
   app. The dialog carries our own hue/saturation/value picker (a
   saturation/value square and a hue slider painted with the painter).
2. **`tools.backgrounds` with no argument reports.** The no-argument
   form now reports the current background and changes nothing (was
   `CommandError::NeedsInput`): the gallery's face click runs the
   opener with no choice, and the old contract put an error on the
   status line every time the gallery opened. The unit test follows.
3. **The Backgrounds control is `kind: gallery`.** It was `kind:
   dropdown` in `panel-modern.yaml`, and the dropdown widget draws
   only its menu items — never its `list` rows — so the gallery could
   not show anything whatever the list held. The control's Fluent type
   is `BackgroundsGallery`; the kind flip is the one-line data fix
   (the v2 count snapshot moves with it: dropdown 32→31, gallery 3→4).
4. **A design owns its named page.** The design page is identified by
   its name ("Background Tint" and friends). `tools.background.color`
   recolours the first `design_colors`-count top-level shapes of that
   page and refuses anything else ("is not a Backgrounds gallery
   background"). Renaming the page breaks the recolour link (it stays
   a usable background page); deleting design shapes makes the recolour
   report "holds no design shapes" once none are left.
5. **`undo_prop.rs` grows a `PREP` seam.** `tools.background.color`'s
   undo-property case gives the page its design background first (one
   staged dispatch, ADR 0040 rule 4); the staged step does not count
   against "one command, one edit".
6. **Data pins.** `ui-spec/commands.yaml` gains the three opener rows
   and `crates/ui-spec/tests/committed.rs` moves the `COMMANDS` pin
   1135 → 1138; `docs/parity/controls.md` is regenerated.

### Open issues

- The coverage ratchets (above): master-owned, one
  `cargo xtask coverage --update-ratchet` on `main` closes it for both
  this task and P7-52.
- The Recent Colors list lives in the egui context store (persisted
  per machine), not in the document: it is picker state, not drawing
  content, and does not save into `.vsdx`.
- The custom colour dialog opens on the selection anchor's resolved
  colour for fill and line; the text role falls back to black when the
  run inherits its colour (the `Character` row read resolves the
  inherited value, not "what it will look like").
- The Backgrounds gallery and Background Color exist in Panel Modern
  (Design > Backgrounds); Panel Classic has no gallery control in its
  layout data, only the link commands (`tools.backgrounds`).
- The gradient and the grid are flat-shape designs: no gradient fills
  (the render layer has none). A future fill type would redraw them
  one shape per design.
