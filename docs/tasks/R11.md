## Goal

From the R9 review (items 3, 7, 8 and 10, and the issue template):

1. **The build id.** The desktop app and the CLI know a build id: the
   short commit SHA from `LARRYGRAM_BUILD_SHA` when the build sets it
   (`release.yml` sets it from `GITHUB_SHA`), otherwise from
   `git rev-parse --short HEAD` when git is there, otherwise `dev`.
   Never fail the build over it. About shows "1.0.0-alpha.1 (abc1234)";
   `larrygram-cli --version` prints the same. The About golden is
   regenerated with a fixed id (set the variable in the test build) so
   it stays stable.
2. **Windows console.** With the GUI subsystem, `larrygram.exe --help`
   and a startup error print nothing. When the app was started from a
   console, attach to it (`AttachConsole(ATTACH_PARENT_PROCESS)`) so
   both print there. This needs `unsafe`: follow ADR 0074's pattern (one
   module, its own `allow`, a comment on each call) and amend ADR 0074
   to name it, or show a message box for a startup error instead if
   you can do it without `unsafe`. Say which and why.
3. **Windows icon resource.** An `.ico` built from the brand
   `icon.svg` at build time, embedded with a permissive crate
   (`winresource`, MIT, or similar; `cargo deny` must pass), so
   Explorer, the zip listing and pins show it. Windows host only; other
   hosts skip it.
4. **Pin `ci.yml`'s actions** to full commit SHAs with version
   comments, as `release.yml` does.
5. **Issue template.** `.github/ISSUE_TEMPLATE/bug.yml` (our own
   words): what happened, steps, the release tag and build id, the OS,
   and an optional drawing. Point testers.md at it.

Run `actionlint` on the workflow and template edits.
