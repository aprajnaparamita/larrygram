## Why

The P7-38 review (2026-11-03) found that every label in the website
shots sits in the top-left corner of its shape. The renderer is right
to read a missing `VerticalAlign` or `HorzAlign` as 0 (top, left):
that is the cell's documented value 0. But Visio files get middle and
centre from their styles, and our own masters and new documents set
neither, so our shapes draw their text top-left. The same shots showed
the Shape Data value "Process" cut to "Proce".

## Goal

1. **Find where the alignment should come from.** Check what a new
   drawing's styles carry today and what our masters carry. Visio's
   default text style centres text in the middle; our files should
   produce the same picture. Pick one of these and say why in the
   Result:
   - the new document's default text style sets `VerticalAlign` 1 and
     the paragraph `HorzAlign` 1;
   - or each master that should centre its text sets them.

   Do not change the renderer's reading of a missing cell.
2. **Centred shapes.** Every Basic Shapes and Basic Flowchart master
   whose text Visio centres draws its text centred, both ways, when
   dropped into a new drawing and when its text is typed. The text
   tool's own text box keeps its current alignment unless Visio's
   differs; say what you found.
3. **Files still open the same.** A `.vsdx` that carries its own
   styles renders as before; the corpus render goldens do not change.
   If one does, stop and report it.
4. **Shape Data values fit.** The value field in the Shape Data pane
   shows the whole value for ordinary values (for example "Process",
   "Decision", a 30-character string), in both layouts, at the
   default pane width; a longer value is cut with an ellipsis and its
   full text in the tooltip.

## Result

_Filled in by the worker at hand-off._

Done 2026-11-03 on `agent/P7-44` (rebased on `main` at `a94ba30`).

**1. Where the alignment comes from.** Checked both sides first: a new
drawing `file.new` creates has an empty stylesheet (no styles at all),
and our masters carried no text cells, so every alignment cell
resolved to its documented default 0 (top, left). Corpus evidence
(committed as `docs/sources.md` row 31): Visio's files reach middle
and centre through their document styles — the `No Style` row of every
corpus file with a stylesheet carries `VerticalAlign` 1 and `HorzAlign`
1 (spot-checked in `blue-box.vsdx`; `Text Only` sets 0/0). **Chosen:
each master that should centre its text sets them** — every master's
sheet gains `VerticalAlign` 1 and one `Paragraph` row (`IX` 0) with
`HorzAlign` 1 (`crates/model/src/stencils/mod.rs`). The other option
needs a change this task does not own: our lookup
(`crates/model/src/lookup.rs`) has no rung that falls back to a
document's default text style, and shapes dropped by `instantiate`
carry no `TextStyle` link, so a style created by `file.new` could not
reach them without a new lookup rung and style links on every dropped
shape. The masters' cells instead travel with the master into every
drawing and every saved file (a dropped instance resolves them through
the master rung, `ValueSource::Master`). The renderer's reading of a
missing cell is unchanged, and a `.vsdx` that carries its own cells
still resolves its own first (the local rung wins), so files open the
same.

**2. Centred shapes.** All 21 masters (12 Basic Shapes, 9 Basic
Flowchart) draw their text centred, both ways, when dropped into a new
drawing and when their text is typed; the two model tests pin both.
The Connector master is included: Visio's `Connector` style carries
`VerticalAlign` 1 and inherits `HorzAlign` 1, so its label is centred
too. The text tool's own text box keeps its current alignment
(top-left: `insert.drawing.text_box` sets no alignment cells, so the
documented defaults 0/0 apply). What I found about Visio's: the corpus
shows Visio gets alignment from styles and carries a `Text Only` style
at 0/0 beside the centred default chain, but which style Visio's Text
tool box carries cannot be established without a Visio black-box run,
so the box stays unchanged (open issue 1).

**3. Files still open the same.** No reader or renderer change; the
corpus render goldens do not change (their tests pass unmodified in
the gate).

**4. Shape Data values fit.** The value field was clamped to 40
points: the egui grid's sizing pass offers a cell almost no width, and
`desired_width` yielded to it (the "Proce" cut). The field now fills
its pane row — pane width minus the widest row label, a 4-point column
gap and 1-point safety margin, capped at 40..400 points — and pins its
size with `min_size`, which overrides the available width. A value
that does not fit the text area is cut with an ellipsis and its full
text is the tooltip (the accesskit description, how the phase 7 checks
read tooltips); while the field has the keyboard focus it shows the
whole text again. At the default pane width (220 points; 203-204 of
content after the side panel's frame) the measured text area is about
155 points beside the pane's own `Name` row label (34 points), so
"Process" (43), "Decision" (49) and a 30-character ordinary string
(the tested "This is a thirty character str" is 153) show whole, in
both layouts; wider values cut (open issue 2). No deviation from the
task text otherwise; no new dependencies.

**Open issues:**

1. The text tool's text box stays top-left. A Visio black-box check of
   the Text tool box (which style it carries) settles whether Visio
   differs; if it does, `insert.drawing.text_box`
   (`crates/commands/src/builtins/insert.rs`, not this task's files)
   needs the alignment cells or a style link.
2. A value wider than the row's text area (~155 points beside the
   `Name` label at the default pane width) cuts with the ellipsis and
   tooltip. A 30-character string of digits or capitals is wider than
   that. Widening `PANES_WIDTH` (220, `crates/ui/src/shell.rs`, not
   this task's files) to about 240 points would fit 30 ordinary
   characters beside any label.
3. The Connector's label sits centred in the master's thin text block
   (on the line). Visio starts connector labels at a movable text
   position above the line (`Controls.TextPosition` and the `Txt*`
   placement cells, as the corpus's connector masters show). A
   connector text-block placement belongs with the connector tasks
   (P7-33 to P7-36).
4. The cut display is one frame behind the keyboard focus: a click
   focuses the field in the frame whose buffer still shows the cut
   text, so a keystroke landing in that same frame would edit the cut
   display. Real typing arrives after the frame turns; the commit path
   validates typed values anyway.
