## Why

The user's manual pass of the build at `205e62f` (2026-11-02):

- With a shape that has no text selected (a circle), every text control
  is still enabled. Left-aligning a circle does nothing visible, so the
  controls look broken. P7-24 item 8 kept them enabled on purpose
  ("the format applies to text typed later"); the user overrides that.
- Double-click and typing a letter do start a shape's text, but the
  user didn't know to try them. Choosing the Text tool while the shape
  is selected did nothing.

## Goal

1. **Text controls follow the text.** With the selection holding no
   shape that has text, the text formatting controls are disabled in
   both layouts: font, size, Bold, Italic, Underline, the alignments,
   and the other character and paragraph commands. The disabled
   tooltip says how to add text, in our own words, for example "Add
   text first: double-click the shape or start typing." They enable as
   soon as the shape has text, and while its text is being edited (the
   format applies to the text being typed). With several shapes
   selected, they are enabled when any of them has text. The fill,
   line and other shape formatting controls are unchanged.
2. **The Text tool on a selected shape.** Choosing the Text tool (the
   button, the menu row or its shortcut) while one shape is selected
   starts editing that shape's text, with the caret at the end. With
   nothing selected, or several shapes, it arms the tool as today.
3. **A Text tool click on any shape** edits that shape's text, not only
   on a text box made with the tool. A click on empty page still starts
   a new text box.
4. **Edit Text in the context menu.** The shape context menu's Edit
   Text row (`context.shape.edit_text`, `text.begin`) starts editing in
   both layouts. Check it works; fix it if it doesn't.

## Result

Done: items 1 to 4, each with real-input tests in both committed
layouts (Panel Classic and Panel Modern) in
`crates/ui/tests/phase7/text_controls.rs`, driven through `ShellRig`
(canvas clicks, tool button clicks, the context-menu row, typed text)
and checked on the enabled state and tooltip through accesskit, on
the shape's cells and on the rendered picture.

**Item 1 — the text controls follow the text.** The font, size and
character/paragraph commands (the 21 ids of `format.rs`'s table: font
and size with their grow/shrink aliases, Bold, Italic, Underline,
Strikethrough (both ids), the font colour and its use-default, the
seven alignments and Bullets) take the new `can_format_text`
predicate: enabled when a selected shape has text (a non-empty
literal part, `text::shape_has_text`), or while one is being edited
(`AppCtx::editing_text`, mirrored from the UI's in-place editor each
frame by `Shell::sync_editing_text`); disabled otherwise with the
reason "Add text first: double-click the shape or start typing.".
With several shapes selected the rule is any-of. The fill, line and
other shape formatting controls keep `can_format`. **This reverses
P7-24 item 8's rule** ("the controls stay enabled on a shape without
text; the format applies to text typed later") at the user's
instruction; the P7-24 task file is untouched, and its goal-8 test in
`manual_fixes.rs` is rewritten for the new rule (disabled with the
hint, enabled while editing, and the format still applies to the text
being typed). The Classic font and size combos never attached their
tooltip, so goal 1's disabled tooltip needed
`panel_classic/toolbar.rs`'s `draw_combo` to carry the activation's
tooltip like the toolbar buttons (a small change outside the owned
files, in the same crate).

**Item 2 — the Text tool on a selected shape.** `tools.text`
(`tools.rs`'s `run_text`) with exactly one live shape selected arms
the tool and returns the new `UiRequest::EditText`; the shell routes
it to `begin_text_editor`. With nothing or several shapes selected it
only arms the tool, as today. The caret sits at the end because the
editor now clears egui's stale cursor state on open
(`text_edit.rs`'s `show`): the field's state persists under its id,
so a re-open of the same shape's text used to keep the old caret
position. Item 2 also covers the menu row and the shortcut: they
dispatch the same command.

**Item 3 — a Text tool click on any shape.** The tool's click path
already hit-tested any shape; `text_controls.rs` pins it on a shape
without text (the user's circle case) and keeps the empty-page case
(a click there still starts a new text box).

**Item 4 — Edit Text in the context menu.** `context.shape.edit_text`
(`text.begin`) was a Panel Modern row only; Panel Classic's shape
context menu now carries the same row
(`ui-spec/layouts/panel-classic.yaml`), so the row starts editing in
both layouts. The count pins follow the new row (the ui-spec v2 count
snapshot, the `panel_classic` count snapshot and the icon counts).

### Deviations and notes

- `UiRequest::EditText` (payloadless) is a new variant in
  `crates/commands/src/lib.rs`: `tools.text`'s handler lives in L4 and
  the editor in L6, so the request is the existing seam (ADR 0028).
- `AppCtx.editing_text: Option<ShapeId>` is new: the enabled
  predicates live in `crates/commands` and the editor state in
  `crates/ui`, so the shell mirrors the field each frame (the same
  window-state pattern as `active_tool`, in reverse).
- The registry's dispatch enforces the enabled predicate, so the text
  formatting commands also refuse programmatically on a shape without
  text now. The commands tests (`formatting_set.rs`, `undo_prop.rs`)
  give their fixture shapes text; `formatting_set.rs`'s render test
  writes the text first and then the format (it used to pre-format).
- Test updates beyond the named `manual_fixes.rs`: `latch_fixes.rs`
  and `combo_fixes.rs` give their fixture shapes text (their contract
  is the latch and the combo, not the enablement); the
  `contexts/crosscheck.rs` allowlist gains the follow-the-text rule
  (the 2007 table's `enabled_in` has no text dimension, and the
  context fixtures' shapes have none); four Phase 7 goldens are
  regenerated for the disabled look (0.03–0.6% of the pixels, all in
  the toolbar regions; the ADR 0027 metric unchanged).
- No new dependencies.
