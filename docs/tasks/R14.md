## Why

The user wants Windows and Linux packages of the alpha now. R9 builds
each platform on its own host and left the Windows and Linux legs to
the CI runners, and GitHub Actions is still billing-locked. The user
chose (2026-11-08) to cross-build both on this Mac (Apple silicon,
macOS).

## Goal

1. **Linux x86_64 from the Mac.** `cargo xtask dist linux --cross`
   builds `x86_64-unknown-linux-gnu` release binaries (`larrygram`
   and `larrygram-cli`) with `cargo-zigbuild` (zig as the C compiler
   and linker), pinned to an old glibc (`x86_64-unknown-linux-gnu.2.31`
   or older, so the binary runs on Ubuntu 20.04 and later), then
   writes the same `.tar.gz` the native path writes. Check what the
   binary links (`llvm-readobj --needed-libs` or `zig`'s tooling):
   only glibc's libraries, with X11/Wayland/GL/xdg-portal loaded at
   run time. If a dependency needs a system library at link time (for
   example GTK through `rfd`), say which, and prefer a pure-Rust
   feature (`rfd`'s xdg-portal backend) over shipping a sysroot.
2. **Windows x86_64 from the Mac.** `cargo xtask dist windows --cross`
   builds `x86_64-pc-windows-msvc` release binaries with `cargo-xwin`,
   then writes the same `.zip` the native path writes. The `.exe`
   carries the Larrygram icon: make `build.rs` embed the resource on a
   non-Windows host when the target is Windows and a resource
   compiler is available (`llvm-rc` from Homebrew LLVM, or whatever
   `winresource` supports cross), and skip it with a warning
   otherwise, never fail.
3. **Without `--cross` nothing changes:** each platform still refuses
   the wrong host with today's message. With `--cross`, a missing
   tool (`zig`, `cargo-zigbuild`, `cargo-xwin`) is a clear error that
   names the install command, before anything builds.
4. **Tools.** Install what the cross builds need, machine-wide, and
   list each with its version and licence in the Result: `zig` and
   `llvm` from Homebrew, `cargo-zigbuild` and `cargo-xwin` with
   `cargo install --locked`. cargo-xwin downloads Microsoft's CRT and
   Windows SDK libraries under Microsoft's licence: keep its cache
   outside the repo, at `/Volumes/Dara/larrygram/xwin` (set
   `XWIN_CACHE_DIR`), and never commit anything from it.
5. **Build both packages** from your branch and report the file names
   and sizes. Leave them in your worktree's `target/dist/`. Check
   each archive's contents from xtask (the read-back the native tests
   use) and check the binaries' headers (`file` should say "ELF
   64-bit LSB pie executable, x86-64" and "PE32+ executable (GUI)
   x86-64").

## Master notes

- Clean-room (AGENTS.md section 4): the Microsoft CRT and SDK are
  link-time libraries, used as any Windows build uses them; nothing
  from them is committed, extracted or redistributed beyond what the
  linker puts in our `.exe`.
- The `ring` cross workaround in R9's Result is no longer needed with
  zig and xwin as the compilers; do not carry it over.
- The xtask tests stay pure: the cross paths run through the `Sys`
  fake like the native ones (no real zig or xwin in unit tests).
- Do not set `CARGO_TARGET_DIR` (AGENTS.md section 2); build in the
  worktree's own `target/`.
- The packages are untested on real Windows and Linux; say so in the
  Result. The master hands them to the user for a first run.
