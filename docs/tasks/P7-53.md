## Why

The user's manual pass of the alpha build (2026-11-05): with text in
a shape, **no type format change reaches the text**, whether the
shape is only selected or its text is being edited. Bold, italic,
font size and the rest do nothing visible.

The format commands exist (P7-24 item 10, P7-21) and their checked
states read the anchor's `Character` and `Paragraph` rows. Find where
the write is lost. Likely places to look: the write goes to a row the
shape does not render from (a local row when the text inherits the
master's rows, or the wrong row index), the edited text's own runs
override the shape-level row, the commit of the editor rewrites the
text without the new format, or the intent never dispatches while
the editor is open.

## Goal

1. **A selected shape.** With a catalog shape (a Basic Shapes
   Rectangle from the stencil, with its master) selected and its text
   set, Bold, Italic, Underline, a font size, a text colour and Align
   Left change the whole text: the cells change and the rendered
   picture changes. One undo step each. Test both layouts with real
   input on the controls, comparing the picture against the plain
   text.
2. **Text being edited.** With the shape's text open in the editor:
   with no text selected, a format applies to the whole text (the
   simple rule for the alpha; say so in the Result); with a range
   selected, it applies to that range only, and the commit keeps it.
   The format shows in the editor field while editing and in the
   drawn text after the commit. Tests with real input, both layouts.
3. **Save and reopen.** A formatted shape's text keeps its format
   through `file.save_as` and `file.open`.

## Result

Done (2026-11-05/06, `agent/P7-53`, on top of `main` at `4090a21`, the
P7-54 merge). Items 1 to 3:

1. **A selected shape (item 1).** The bug the manual pass reported is
   not reproducible at this level: with a Basic Shapes Rectangle from
   the stencil selected and its text set, Bold, Italic, Underline,
   36 pt, the text colour and Align Left already reach the cells and
   the picture on unmodified code, in both layouts (probed first, then
   pinned). `crates/ui/tests/phase7/text_format_apply.rs` drives each
   control with real input on the catalog shape and compares the
   picture against the plain text (`text_differ`), one undo step each.
   Where the write was actually lost is item 2's path (below): the
   user's "nothing visible" matches the editor's field and the range
   case.
2. **Text being edited (item 2).** Three real defects, fixed:
   - *The selection died on every format click.* egui collapses a
     selection to its primary caret on the frames the field loses the
     keyboard (a format control click keeps the edit but takes the
     keys back, task P7-41), so a selected range was gone before the
     command dispatched. `text_edit.rs` keeps the range across those
     frames and the field re-shows it.
   - *The commit rewrote the text without the run structure.* An
     unchanged buffer committed nothing even when the runs had
     changed, and the one-run collapse dropped every run marker. The
     editor now tracks the runs of the buffer (the `Character` row
     `IX` per run), remaps them over typing, and the commit writes the
     markers (`shape.set.text`'s `run_ixs`/`run_texts` form).
   - *A format with a range selected reached the whole text.* The
     editor splits its runs at the range and the write is scoped to
     the range's runs (`runs`/`runs_keep` on the text format
     commands): each covered run gets its own local `Character` row,
     seeded from the run it splits (ADR 0013: local rows, the master
     never edited), and the runs outside the range keep their rows.
   The alpha rule (to say here as the goal asks): **with no text
   selected a format applies to the whole text**; with a range
   selected it applies to that range only and the commit keeps it.
   The paragraph formats (alignment, bullets) apply to the whole text
   even with a range selected; the range scope covers the character
   formats (font, size, bold, italic, underline, strikethrough,
   colour). The editor field shows each run's format while editing
   (a rich layout over the plain buffer: face, size, colour,
   underline), so a format is visible before the commit.
3. **Save and reopen (item 3).** A formatted shape keeps its format
   through `file.save_as` and `file.open` (cells and drawn text,
   `crates/commands/tests/text_format.rs`); it needed no fix.

### Deviations

- `crates/ui/src/theme.rs` (not in the listed files) registers the
  bundled Carlito and Selawik faces as named egui families: without a
  registered face egui cannot draw a run's bold or italic in the
  field, so goal 2's "the format shows in the editor field" needed
  it. The faces come from `larrygram-text`'s `CARLITO`/`SELAWIK`

  structured form) beside its `text` argument; the one-run form is
  unchanged.
- The text format commands gained the `runs`/`runs_keep` arguments
  (the range scope). A scoped write lands on the shape being edited
  only; an unscoped one behaves exactly as before.
- The unit test `text_edit::tests::begin_plain_text_and_finish_a_changed_buffer`
  now expects the run structure to survive the commit (P7-53's "the
  commit keeps it" replaces the P5-07 collapse for `Character` runs;
  the paragraph and tabs markers still collapse to the first row).

  runs outside the range keep the old row); a "use default" scoped
  write removes the entry from the named rows only.
- `text.cancel` after a range format leaves the created run rows in
  the sheet (the undo steps remove them one by one); orphan rows are
  not rendered (no run marker names them), but a tidy could fold them
  into the cancel.
