## Why

The Opus review of P7-44 (2026-11-03) found goals 1 to 3 done and the
choice of fixing the masters (not the default style) sound, but:

- the 30-character case of goal 4 is likely cut in the real shell: the
  rig draws the pane at a full 220 points, the shell gives it about
  204, and the field's width follows the widest label ("Process" on a
  Process shape, wider than "Name"), leaving about 148 points for a
  153-point string;
- shapes drawn with the Rectangle and Ellipse tools have no master and
  set no alignment, so their text still sits top-left: the same bug;
- the ellipsis rewrites the field's edit buffer, so the field's
  accessibility value is the cut text, focus lags a frame, and egui's
  field undo may bring the cut text back as the value;
- nothing tests that an instance's own alignment wins over the
  master's new Paragraph row, or that the master's cells survive save
  and reopen;
- the label/value gap is now 4 points in every pane, which crowds the
  read-only rows.

## Goal

1. **The pane fits a 30-character value.** Widen `PANES_WIDTH` to
   about 240 points (enough that the 30-character case fits with the
   widest label of a real Process shape). Add the 30-character value to
   the full-shell test (`text_centered.rs` or a sibling) on a Process
   shape dropped from the Shapes window, in both layouts, and assert
   the field shows it uncut. Keep the rig test.
2. **The gap.** Put the label/value gap back to about 8 points if the
   wider pane leaves room; otherwise give the read-only rows their old
   gap and keep 4 only between a label and an editable field. Say which
   in the Result.
3. **Drawn shapes are centred.** `insert.drawing.rectangle` and
   `insert.drawing.ellipse` set `VerticalAlign` 1 and one Paragraph row
   with `HorzAlign` 1 on the new shape, as our masters now carry. Do
   not change the text box tool (P7-44 open issue 1 waits on a Visio
   check). Test both in `crates/commands`, and one through the shell:
   draw a rectangle with the tool, type a label, and check its ink box
   is centred (reuse the P7-44 helper).
4. **The ellipsis is drawn, not stored.** Keep the field's buffer
   whole. While the field is not focused, cut only what is drawn, with
   a `TextEdit` layouter (one row, `overflow_character` `…`) or the
   equivalent. Give the field an explicit id and decide focus from
   `memory.has_focus(id)`, so there is no one-frame lag. Test: the
   accessibility value is the full text while unfocused and the drawn
   text ends in `…`; focusing shows the full text on the first frame;
   Ctrl+Z inside the field after an edit never commits text with `…`.
5. **Local alignment wins, and the master survives a round trip.** A
   commands test: drop Process, run `format.text.align_left`, and check
   `HorzAlign` resolves to 0 from the instance's own row, not the
   master's. A save and reopen test: the master's `VerticalAlign` and
   its Paragraph row are in the reopened file, and an instance still
   resolves to 1/1.

## Result

_Filled in by the worker at hand-off._

Done 2026-11-03 on `agent/P7-44`, rebased on `main` at `08e4d7c`; the
P7-45 commits sit on top of P7-44's. No new dependencies.

**1. The pane fits a 30-character value.** `PANES_WIDTH` goes from 220
to 240 points (`crates/ui/src/shell.rs`, the constant only). At the
default width the real shell gives the pane about 223 points of
content; the widest label of a real Process shape ("Process", 43
points) leaves the field about 171 points and its text area about 163,
so the 30-character case ("This is a thirty character str", 153
points) fits with room. The full-shell test types the 30-character
value into a dropped Process shape's `Cost` row through the pane field
and reads it back uncut, in both layouts
(`crates/ui/tests/phase7/text_centered.rs`); the rig case is kept and
now runs at the 240-point default width
(`crates/ui/tests/pane_values.rs`).

**2. The gap.** Back to one uniform 8-point label/value gap
(`FIELD_GAP`): the wider pane leaves room, so the read-only rows and
the editable fields share the ordinary gap again.

**3. Drawn shapes are centred.** `insert.drawing.rectangle` and
`insert.drawing.ellipse` set `VerticalAlign` 1 and one `Paragraph` row
(`IX` 0) with `HorzAlign` 1 on the new shape
(`crates/commands/src/builtins/insert.rs`, the cells only), the same
cells our masters carry. The text box is untouched (it waits on the
Visio check, P7-44 open issue 1) and the line tool is outside the
task's files (open issue 1). Tests: `drawn_rectangles_and_ellipses_centre_their_text`
and `the_line_and_the_text_box_keep_the_documented_defaults`
(`crates/commands/tests/text_centering.rs`), and one through the
shell: `a_drawn_rectangle_draws_its_label_centred`
(`text_centered.rs`) draws with the Rectangle tool (the Drawing
toolbar), types a label and checks the ink box sits in the middle of
the shape's box, both ways.

**4. The ellipsis is drawn, not stored.** The field's buffer always
holds the whole value; while the field is not focused only the drawing
is cut, through a `TextEdit` layouter (one row, `overflow_character`
"…", `TextWrapping::max_rows` 1, `break_anywhere`). The field has an
explicit id (`TextEdit::id`) and the layouter decides `cut` from
`memory.has_focus(id)` at layout time, so the first focused frame
draws the whole text; the full text stays in the tooltip when the
drawing is cut. Tests: the panes unit tests pin the galley (a cut job
keeps `job.text` whole while the drawn row is elided and ends in "…";
an uncut job draws the whole text), and `pane_values.rs` pins that the
accessibility value is the full text while unfocused, that focusing
redraws the field whole on the first frame (the pixel crop of the
field differs between the unfocused frame and the first focused
frame, with the focus landing in one step), and that Ctrl+Z inside the
field after an edit never commits text with "…" (the committed
`data.set.property` argument is checked).

**5. Local alignment wins; the master survives a round trip.**
`crates/commands/tests/text_centering.rs`:
`local_alignment_wins_over_the_master_paragraph_row` drops Process,
gives it text (the formatting commands' `ADD_TEXT` predicate), runs
`format.text.align_left`, and checks `HorzAlign` resolves to 0 from
`ValueSource::Local` (the instance's own row) while `VerticalAlign`
stays 1 from the master rung;
`the_masters_alignment_survives_save_and_reopen` writes the document
to `.vsdx`, reads it back, and checks the master's `VerticalAlign` and
its Paragraph row are in the reopened file with the instance still
resolving 1/1.
