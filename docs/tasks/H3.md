# H3: Locked release builds, an explicit release profile, plain tester wording

- Role: master (small; the master does it on `main`)
- Phase: hardening (the 2026-11-13 design and security review, finding F7)
- Depends on: none
- Parallel-safe with: H1, H2, P9-17

## Goal

1. `cargo xtask dist` builds with `--locked` (the plain, zigbuild and
   xwin builds), so a release never resolves a dependency the lockfile
   does not name.
2. The workspace `Cargo.toml` writes out `[profile.release]` with
   cargo's release defaults, so the shipped profile is a decision.
   `panic = "unwind"` is required by the planned panic boundary (H10);
   overflow checks stay off until that boundary exists (a checked
   overflow would end the app instead of wrapping) and are revisited
   with H10.
3. `docs/building/testers.md` keeps the Gatekeeper and SmartScreen
   steps but says plainly that they turn a protection off for this
   app, to be used only on the official package checked against
   `SHA256SUMS`, and that signed builds are planned for the beta (user
   decision 2026-11-13: signing and notarisation after the alpha).

Out of scope until the beta: signing, notarisation, and a signed
checksum file or build attestation (F7 second point).

## Acceptance criteria

- [x] Both build steps pass `--locked`; the dist tests expect it.
- [x] `[profile.release]` written out with the defaults and the
      reasons.
- [x] The tester guide wording.
- [x] `cargo test`, `clippy` and `fmt` for xtask; the merge gate with
      the next batch.

## Result

Done by the master on 2026-11-13. `--locked` follows `--release` in
`build_release` (plain and zigbuild) and `build_release_xwin`; the
five dist tests expect it (427 xtask tests pass). The release profile
values are cargo's defaults, so the shipped binaries do not change.
The tester guide adds one paragraph under the macOS steps and one
sentence each to the `xattr` and SmartScreen steps.
