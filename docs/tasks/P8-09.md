## Goal

1. **The open command.** `file.open` accepts `.vsd`, `.vss` and `.vst`
   alongside `.vsdx`/`.vssx`/`.vstx`, routes them to
   `larrygram-vsd-binary::import`, and lands the result in the model
   the editor already opens. Every import warning surfaces as a status
   message list, never silently.
2. **Save defaults.** A document opened from a binary file saves as
   `.vsdx` (the same document-kind mapping the writer uses); the
   binary formats are read-only and the Save As dialog offers only the
   XML formats for them.
3. **The dialog filter and the CLI.** The file dialog filter lists the
   binary formats, and the CLI accepts them as input files (the CLI is
   the same command registry, ADR 0028). An unsupported file (for
   example a version 1–5 `.vsd`) produces a clear user-visible error
   naming the reason (`Error::UnsupportedVersion`), never a crash.
4. **Tests.** Command-level tests with a corpus `.vsd` (skip cleanly
   when the corpus is absent), the filter list, and the CLI path.

## Acceptance criteria

- [ ] A corpus `.vsd` opens through the command, the dialog filter and

## Result

Filled in by P8-09 at hand-off (branch `agent/P8-09`).

**What changed**

- `crates/commands/src/builtins/file.rs` (owned): the open path routes
  by extension. `.vsd`, `.vss` and `.vst` go to
  `larrygram-vsd-binary`'s `import`; every other extension keeps the
  `.vsdx` reader. The imported document lands in the same
  `DocumentSession` the editor opens (`file.open`, and with it
  `inspect`, `render`, `export` and the CLI). Every import warning is
  formatted as one status line of our own words and surfaces both in
  `Outcome::warnings` (the CLI prints them on stderr, `--strict` exits
  4) and on `AppCtx::warnings` (the status list), never silently.
- Save defaults: `file.save` maps a binary session path to the XML
  format of the document kind (`save_target`, the same mapping the
  writer's content types use: drawing → `.vsdx`, stencil → `.vssx`,
  template → `.vstx`), writes there and re-homes the session on the
  written file. The binary formats are read-only: `file.save` /
  `file.save_as` with a `.vsd`/`.vss`/`.vst` `path` is refused with
  `cannot write output: …: the binary Visio formats are read-only;
  save as <target>` and writes nothing. The no-target save suggests
  the kind name (`drawing.vsdx`, `stencil.vssx`, `template.vstx`), and
  the wasm download name maps a binary source name the same way.
- `crates/ui` (owned): `OPEN_EXTENSIONS` lists `vsdx, vssx, vstx, vsd,
  vss, vst` (the open dialog accepts the binary formats), and
  `SaveRequest` gained an `extensions` field so the Save As dialog
  offers the XML formats only (`SAVE_EXTENSIONS`); the rfd save dialog
  filters by it. All `SaveRequest` constructors updated (two in
  `shell.rs`, the test in `dialogs.rs`; the picker fakes in
  `apps/larrygram/tests` and `crates/ui/tests` only implement the
  trait and needed no change).
- `apps/larrygram-cli` (owned): the usage text names every input
  format; the CLI needed no routing change of its own because it
  dispatches the same registry (`file.inspect`/`render`/`export`), and
  the open path in `file.rs` now routes by extension. Tests cover the
  binary input through the registry (inspect and render) and the
  unsupported-version error.
- Unsupported versions (e.g. the version 5 corpus files) fail with
  `cannot read input: <file>: unsupported file version 5 (alpha reads
  6 and 11)` (`Error::UnsupportedVersion`), exit code 2 on the CLI,
  nothing panics.

**Tests** (all with the corpus-skip convention
`LARRYGRAM_REQUIRE_CORPUS=1` where the fetched corpus is needed; the
committed fixture `corpus/fixtures/minimal-drawing.vsd` needs no skip)

- `crates/commands`: the fixture opens through `file.open` with its
