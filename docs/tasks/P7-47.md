## Why

The P7-42 review (2026-11-03) found that `file.save` calls
`save_document(.., false)`, so on a drawing that was never saved the
path picked in the save dialog is written to but not kept. A new
drawing, Cmd+S, pick `a.vsdx`: the title still reads "Untitled", and
the next Cmd+S opens the picker again. Visio keeps the path. The bug
is older than P7-42; P7-42's title test asserts the old behaviour.

## Goal

1. **Confirm it.** Find the path from the picker to `file.save` and
   check the review's reading. Say in the Result what you found.
2. **Keep the path.** When `file.save` runs on a document with no
   path and is given one (the picker's answer), the path becomes the
   session's path and is recorded as a recent file, as Save As does. A
   `file.save` with a path on a document that already has one keeps
   today's behaviour; say what that is.
3. **Tests.** In `crates/commands`: the path is kept and the drawing
   reads unchanged after the save. Through the shell with real input,
   both layouts: a new drawing, Save, pick a path, then the title shows
   the file name with no changed marker, and a second Save writes again
   without asking. Change the P7-42 title assertion to match.

## Result

**Item 1 — confirmed.** The picker's answer reaches `file.save` as the
`path` argument: `Shell::ask_picker` (`crates/ui/src/shell.rs`) answers
the `NeedsInput(NeededInput::Path { purpose: PathPurpose::SaveFile, .. })`
of a target-less save with `Ask::Again(with_choice(..))`, which re-runs
the same invocation with `path` set. `run_save` called
`save_document(ctx, inv, false)`, and `save_document` only kept the
path when `set_path` (Save As) or the binary-mapping case held. So the
file was written to the picked path but `session.path` stayed `None`:
the title kept reading "Untitled" and the next save opened the picker
again. The P7-42 review's reading is right; the bug predates P7-42.

**Item 2 — the path is kept.** `save_document` now re-homes the session
when `set_path || mapped || own.is_none()`: a `file.save` on a document
with no path adopts the picked path as the session's path, and
`remember_recent` (which already ran) records it as a recent file, as
Save As does. Today's behaviour kept for `file.save` naming a path on a
document that already has one: the file is **written to the named
path** and recorded as a recent file, but the **session stays on its
own path** (only `file.save_as` re-homes that one) — pinned by
`a_named_save_of_a_saved_drawing_keeps_its_own_path`.

**Item 3 — tests.**
- `crates/commands` (`builtins/file.rs`):
  `a_save_of_an_unnamed_drawing_keeps_the_picked_path` — the picked
  path becomes the session path and a recent file, the save records
  the saved state, the in-memory drawing is untouched and the written
  file reads back as the same document;
  `a_named_save_of_a_saved_drawing_keeps_its_own_path` — the pin of
  today's behaviour above.
- Through the shell with real input in both layouts
  (`crates/ui/tests/phase7/unsaved.rs`):
  `saving_an_unnamed_drawing_keeps_the_picked_path` — a new drawing
  edits, Cmd+S, the test file picker picks a temp path: the title
  shows the file name with no changed marker and the window title
  follows; a second Cmd+S writes the kept path again with no second
  pick (the first file is deleted and comes back). The P7-42 title
  assertion (`the_title_shows_the_marker_and_loses_it_after_a_save`)
  now expects the saved file's name instead of "Untitled".
