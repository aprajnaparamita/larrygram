## Why

The `.vsdx` reader builds a full `XmlNode` tree for every XML part.
`Limits` caps bytes, depth, entries, the compression ratio and the
attributes per element, but not the number of nodes, and each node
owns three strings (`QName` in `crates/model/src/raw.rs`). The review
measured about 45 bytes of RAM per byte of XML: a 5.7 MB file with
one extra, unreferenced part of tiny elements with random two-letter
names (random names keep deflate under the 200:1 cap) peaked at
744 MB in `larrygram-cli inspect`. At the current caps one 64 MB part
reaches about 3 GB. The full numbers are in
`/Volumes/Dara/larrygram/review-2026-11-13-prompt.md`, F1.

This task adds the budget. Cutting the per-node cost (sharing the
namespace URI) is a later task (H4) and changes `model`; do not touch
`QName` here.

## Goal

1. **Two new caps in `Limits`**, checked in `parse_xml` before each
   node or attribute is stored:
   - `max_xml_nodes`: elements plus text nodes, counted across the
     whole package (all parts together), so many medium parts cannot
     add up to the blow-up either;
   - `max_xml_attributes`: attributes across the whole package.

   Over budget is `Error::LimitExceeded` with the cap's name, the
   count reached and the cap, like the existing caps. Thread one
   running counter through `read_package` (a small struct passed by
   `&mut` to each `parse_xml` call is fine); keep `parse_xml`
   `pub(crate)`.
2. **Defaults from the corpus.** Count the nodes and attributes of
   every file in `corpus/vsdx/` (a test or a throwaway program in your
   worktree; link `corpus/` as AGENTS.md section 3 says). Set each
   default to a round number about 20 times the largest file's count,
   and record the measured maxima and the chosen defaults in the
   ADR 0017 amendment and in your Result. A default that would let
   one file reach more than about 1 GB of tree at today's cost
   (roughly 200 bytes per node) is too high: say so in the Result if
   the corpus forces it.
3. **Regression tests.**
   - A package built in the test (the shape of the review's repro: a
     valid small drawing plus one extra part of many tiny elements
     with varied names) with a low `max_xml_nodes` passed in `Limits`,
     asserting `LimitExceeded { limit: "max_xml_nodes", .. }`; the
     same for attributes.
   - The default caps still open every corpus file (the existing
     corpus tests cover this; say which ones ran).
   - A test that the count spans parts: two parts each under the
     budget, together over it, are refused.
4. **A fuzz seed.** Add one small package of the repro shape (a few
   KB) to the `read_package` seed corpus.
5. **The `.vsdx` peak, re-measured.** Rebuild the review's 16 MB repro
   in a temporary directory and run
   `/usr/bin/time -l target/release/larrygram-cli inspect <file>` from
   your worktree's release build (`cargo build --release -p
   larrygram-cli`; one build, not a workspace command). Report the
   peak RSS before (744 MB, the review's number) and after. Delete the
   file afterwards.
